## 1. الغرض والقرار التنفيذي

هذا السجل هو مرجع متابعة موحد للمحركات الخمسة عشر في Raven OS. الغرض منه ربط كل محرك بمسؤوليته ومصادره ومستهلكيه واعتمادياته وبوابات تفعيله واختبارات قبوله، مع منع ازدواج البيانات أو الادعاء بوجود وظائف غير متصلة.

**قرار معماري:** لا تُنشأ خمسة عشر نظامًا أو قاعدة بيانات مستقلة. تستخدم المحركات طبقة مشتركة للهوية الموثوقة، والصلاحيات، ونطاق المدرسة، والبيانات المدرسية المرجعية، والتخزين الآمن للملفات، وسجل التدقيق، والأحداث والمراقبة. يبقى لكل محرك عقد نطاق وخدمات وواجهات واختبارات مستقلة.

**حدود هذا السجل:** لا يختار مزود هوية أو قاعدة بيانات أو ORM أو خدمة تخزين ملفات أو مزود تكامل خارجي. ولا ينشئ جداول أو migrations أو اتصالات أو بيانات تجريبية. هذه قرارات تصميم منفصلة تتطلب حصر المصادر الخارجية وقرارًا معماريًا وموافقة المالك.

## 2. مقياس الحالة

| الحالة | معناها في هذا السجل |
|---|---|
| أخضر — مكتمل ومختبر | تنفيذ فعلي مع اختبارات قبول موثقة على النطاق المحدد |
| أزرق — تصميم/عقد | بنية أو عقد أو مواصفات موثقة، دون ادعاء تشغيل |
| أصفر — معتمد لاحقًا | نطاق معتمد للتنفيذ في مرحلة لاحقة |
| برتقالي — قيد الاختبار | تنفيذ موجود ويخضع حاليًا لاختبارات موثقة |
| أحمر — غير منفذ | لا يوجد تنفيذ قابل للاستخدام |
| بنفسجي — Prototype | نموذج أولي لا يعد خدمة إنتاجية |

**الحالة الفنية الحالية في سجل المحركات البرمجي:** جميع المحركات الـ15 تحمل `architecture`. توجد عقود نطاق أولية للمحركات 1–5 وأساس معماري مشترك، لكن لا يوجد محرك مثبت كـ `connected` أو `verified`. لذلك لا نمنح أي محرك اللون الأخضر أو البرتقالي لمجرد وجود اسمه أو واجهته.

## 4. الطبقة المشتركة التي تخدم المحركات

| الخدمة المشتركة | المسؤولية | بوابة التفعيل المطلوبة |
|---|---|---|
| الهوية والجلسات | إثبات هوية المستخدم وإدارة دورة الحساب والجلسة | تحديد مصدر الحسابات الخارجي، مالكه، آلية الربط، ثم اعتماد مزود الهوية |
| الصلاحيات ونطاق المدرسة | التحقق من الدور والعملية والمدرسة والسجل والعلاقة | مصفوفة أدوار وأفعال معتمدة، واختبارات منع الوصول غير المصرح |
| مركز البيانات المدرسية الموحد | المرجع القانوني/التشغيلي للسجلات المدرسية ومفاتيحها وعلاقاتها | اعتماد مصادر كل نطاق وقواعد التعارض والترحيل |
| مستودعات البيانات | تنفيذ القراءة والكتابة والمعاملات والقيود والتفرد والتزامن | قرار قاعدة البيانات والمخطط والمهاجرات والنسخ الاحتياطي والاستعادة |
| الملفات والمرفقات | حفظ المصدر والإصدارات والتحقق والفحص والتنزيل المصرح | قرار التخزين وسياسة الفحص والتشفير والاحتفاظ |
| سجل التدقيق | سجل دائم غير قابل للتعديل العادي ومتزامن مع الكتابة | sink دائم، صلاحيات الاطلاع، سياسة الاحتفاظ، واختبارات الذرية |
| الأحداث والمهام | نشر أحداث موثوقة ومعالجة إعادة المحاولة والتكرار | عقد أحداث، outbox/queue مناسب، idempotency ومراقبة |
| المراقبة والتشغيل | قياس الصحة والأخطاء والتنبيه والتتبع | تحديد مؤشرات تشغيل وحدود تنبيه دون بيانات شخصية غير لازمة |

لا تُعد هذه الخدمات مزودين أو منتجات مختارة؛ إنها مسؤوليات منطقية يجب تنفيذها ضمن المسار التقني المعتمد للمشروع.

## 5. تسلسل التنفيذ وبوابات الخروج

### المرحلة A — إغلاق اكتشاف المصادر والهوية
- حصر مصدر حسابات الموظفين والأسر ودورة إنشاء الحساب وتعطيله.
- تحديد مصدر المدرسة الرسمي ومعرّفها الثابت.
- تحديد مصادر عضوية الموظفين وتكليفات المعلمين والفصول.
- تحديد مصدر الطالب والتسجيل والولي/العلاقة المعتمدة.
- تحديد ملاك البيانات، وآليات التصدير أو API المسموحة، وتواتر التحديث وحقوق التكامل.
- توثيق ADR للهوية والجلسات ومصفوفة الأدوار بعد اكتمال الاكتشاف.

**بوابة الخروج:** مصادر موثقة ومالك لكل مصدر، قرار هوية معتمد، ومصفوفة صلاحيات معتمدة. لا تُنشأ حسابات أو جلسات فعلية قبلها.

### المرحلة B — اعتماد بنية التخزين والبيانات
- مراجعة النموذج الموحد وقاموس الحقول والعلاقات ومفاتيح الربط.
- اعتماد قاعدة البيانات وطريقة migrations والقيود والفهارس.
- تصميم tenant isolation على مستوى الخادم/قاعدة البيانات.
- تصميم repositories وunit-of-work والمعاملات والتزامن ومنع التكرار.
- اعتماد التخزين الآمن للملفات والنسخ الاحتياطي والاستعادة والاحتفاظ.
- اعتماد سجل تدقيق دائم متزامن ذريًا مع عمليات الكتابة.

**بوابة الخروج:** ADR معتمد، مخطط قابل للمراجعة، خطة ترحيل واستعادة، واختبارات أمن سلبية قبل أي بيانات حقيقية.

### المرحلة C — تشغيل المحركات 1–5
1. تنفيذ مستودعات البيانات المدرسية والتحقق والاستيراد المرحلي.
2. تنفيذ القرارات والتكليفات مع دورة الموافقة.
3. تنفيذ سير العمل والمتابعة والتواريخ والتكرار.
4. تنفيذ الملفات والأدلة والمراجعة والقبول والأرشفة.
5. تنفيذ الخطط والإصدارات والأهداف والمبادرات وربطها بالمراجع الأصلية.

**بوابة الخروج:** اختبارات CRUD ودورات الحالة، عزل المدارس، صلاحيات السجل، الذرية بين الكتابة والتدقيق، التكرار، الاستعادة، واختبارات تكامل من واجهات الخادم.

### المرحلة D — تشغيل المحركات 6–10
- التقويم والاعتماد ثم نافس والقياس بعد اعتماد مصادر النتائج.
- الأمان والحماية والحوكمة والصلاحيات كضوابط مستمرة وليست شاشة فقط.
- المساعد الذكي بعد إثبات الهوية وحدود الاسترجاع ومصادر البيانات، مع منع الاعتماد أو التنفيذ الآلي.
- التوصيات لا تصدر قرارًا ولا تغير خطة معتمدة دون إجراء بشري مصرح.

### المرحلة E — تشغيل المحركات 11–15
- التكامل الداخلي وتبادل البيانات أولًا.
- موصلات الأنظمة التعليمية بعد إثبات API/الآلية الرسمية والتفويض.
- أدوات رافين كعمليات مراجعة/معاينة/تأكيد، لا كأتمتة تتجاوز الأنظمة.
- تكامل منصات مؤسسة رافيين بعد تحديد المالك والعقود والموافقات وفصل البيانات.

## 6. اختبارات القبول المشتركة الإلزامية

كل محرك يمر بالاختبارات المشتركة التالية، إضافة إلى اختبارات مجاله:

1. **الهوية:** رفض المستخدم المجهول والجلسة المنتهية والحساب المعطل.
2. **الدور:** رفض الدور الذي لا يملك الإجراء المطلوب حتى لو كان يستطيع فتح الصفحة.
3. **عزل المدرسة:** مستخدم المدرسة A لا يقرأ أو يكتب سجل المدرسة B بتغيير URL أو body أو filter أو export.
4. **نطاق المورد:** المعلم لا يصل إلى فصل/طالب غير مسند إليه، والأسرة لا تصل إلا لعلاقة ولي موثقة وفعالة.
5. **الذرية:** فشل حفظ السجل أو حدث التدقيق يؤدي إلى rollback للمعاملة كاملة.
6. **التكرار:** إعادة إرسال المفتاح نفسه لا تنشئ سجلًا أو أثرًا مكررًا.
7. **التزامن:** منع الكتابة الصامتة فوق نسخة أحدث؛ استخدام version/concurrency token.
8. **دورة الحياة:** رفض انتقالات الحالة غير المسموحة وعدم اعتبار المسودة موافقة.
9. **الملفات:** لا تنزيل أو معاينة قبل التحقق من الصلاحية وسلامة الملف ونطاق المدرسة.
10. **التدقيق:** تسجيل الفاعل والدور والمدرسة والفعل والنتيجة والوقت وcorrelation ID دون أسرار أو بيانات شخصية غير لازمة.
11. **الاستعادة:** إثبات استعادة نسخة احتياطية في بيئة اختبار.
12. **التشغيل:** Build وTypeScript وLint واختبارات الوحدة والتكامل وE2E والأمن حسب نطاق التغيير.

## 7. قرارات المالك المطلوبة قبل التنفيذ الحي

هذه أسئلة حاكمة لم تُحسم في المستودع، ولا يجوز استنتاج إجاباتها:

- ما النظام الحالي الذي تنشأ وتدار فيه حسابات الموظفين والأسر؟ ومن مالكه؟
- ما المصدر الرسمي لمعرّف المدرسة والموظف والطالب والعضوية والتكليف والعلاقة بين ولي الأمر والطالب؟
- هل توجد أنظمة داخل المؤسسة أو ملفات Excel/تصديرات رسمية يجب الحفاظ عليها أو استيرادها؟
- ما مصدر الحقيقة عند اختلاف بيانات Raven مع مصدر خارجي؟ ومن يملك قرار التصحيح؟
- ما مدد الاحتفاظ والحذف والاسترجاع لكل فئة من البيانات والملفات؟
- من يعتمد كل نوع من القرارات والتكليفات والاستيرادات وتغييرات البيانات؟

لا نطلب كلمات مرور أو مفاتيح API أو أسرارًا في هذه المرحلة. يكفي تحديد اسم المصدر ومالكه وآلية الربط المسموحة.

## 8. قيود لا يجوز تجاوزها

- لا تعديل على `main`، ولا دمج، ولا نشر إنتاجي دون موافقة صريحة مستقلة.
- لا تعديل على مستودع Design Arena الأصلي.
- لا إدخال بيانات طلاب أو موظفين حقيقية قبل اجتياز بوابات الأمن والعزل والخصوصية.
- لا بيانات وهمية أو مؤشرات أو إشعارات أو نجاحات محاكاة.
- لا اعتماد مزود هوية أو قاعدة بيانات أو تخزين أو شركة تكامل دون ADR ومناقشة واعتماد.
- لا تحويل واجهة مرئية أو عنصر تنقل إلى ادعاء بأن المحرك يعمل.
- لا استخدام إخفاء الواجهة بديلًا عن التحقق الخادمي.
- لا نسخ بيانات رئيسية بين المحركات؛ المرجع المدرسي الموحد يملك السجل، والمحركات الأخرى تحفظ المراجع والأحداث اللازمة فقط.
- لا تنفيذ تلقائي لقرارات أو موافقات أو تغييرات خطط معتمدة بواسطة المساعد الذكي أو التوصيات.
